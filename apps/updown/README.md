# Up Down

A Cato-inspired Up/Down price-call game, built on an Orderly SDK 3.1.11 integration and the official Orderly DEX template (upstream MIT license retained).

## Run locally

From cato-wrapped/apps/updown:

    npm run dev

Open http://127.0.0.1:5185. This starts Vite and a separate loopback round service on port 5186. Both must be running for the complete experience. Worker code changes require a worker restart; the browser only shows Increase time when health reports support. Existing journals need no migration. Restart when there are no active rounds to avoid interrupting their scheduled closes. Use npm run dev:web / npm run dev:worker separately if needed. Restart both after changing .env; do not change networks with an active round.

The public mainnet configuration lives in this app's gitignored .env. WalletConnect remains unconfigured. Real trades and funding require the user's wallet interaction. A fresh checkout using .env.example starts on testnet/demo.

Dependencies are pinned in this app's package-lock.json and install independently of the root workspace (the root package.json lists only the deployed apps):

    npm ci --legacy-peer-deps

The lockfile was resolved with legacy peer-dependency handling (the Orderly wallet packages have conflicting peer ranges), so a plain `npm ci` reports it as out of sync. Use the same flag for `npm install`.

Node 22.12+ is recommended because some transitive wallet packages require it. The current local Node 20.19 passed compilation/tests/build, but emits dependency engine warnings.

## Inside the main site

The game is served by the main site (apps/web) under /updown, so both share one origin: the wallet a player connected on the site reconnects here without a new approval, and one cookie jar covers both. The site's middleware blocks /updown and /game-api without a beta session cookie, which /play issues only after the wallet signs a sign-in message and holds at least UPDOWN_VIP_THRESHOLD CATO (default 50,000).

Production (Vercel, the site's only host): `npm run build` in apps/web first runs apps/web/scripts/build-updown.mjs, which installs this app with `npm ci --legacy-peer-deps`, builds it with VITE_BASE_URL=/updown/ and a 3 GB heap, and copies build/client to apps/web/public/updown. The site serves that bundle with an SPA fallback. The round service runs as the site's own serverless route handlers (apps/web/app/game-api) using this app's server/engine.mjs, server/service.mjs and server/postgres-store.mjs on the website's Postgres (DATABASE_URL); there is no long-running worker there. See "Serverless round service" below.

Local development: run `npm run dev` here and `npm run dev` in apps/web, then open http://localhost:3000/play. `next dev` proxies /updown to this Vite server. /game-api is then the site's route handler, which needs DATABASE_URL and UPDOWN_JOURNAL_KEY in apps/web's environment; to use this app's standalone worker instead, set UPDOWN_WORKER_ORIGIN=http://127.0.0.1:5186 for `next dev`. Set VITE_BASE_URL=/ to run the game on its own (http://127.0.0.1:5185, with the worker on :5186) again.

## First draft

- All active markets available to the broker, searchable in a picker; one market shown at a time. Asset icons use the installed Orderly SDK official CDN convention, including broker-symbol fallback; unavailable images fall back to initials in the picker, selected market, latest round and history.
- Live mark price and an SVG line chart with 5/15/90-minute windows (5 minutes by default). Completed candle closes form the muted history. Observed live segments are green for estimated net profit and red for loss after trading fees; pre-round and unknown estimates stay grey. Historical colors retain their observed fee/position basis after subsequent prices, partial closes and later rounds. Capture is local to the mounted chart and resets on account/market changes or reload; earlier candles are not reconstructed as sub-minute round history. Candle closes use the end of their minute and refreshed history cannot overlap the live timeline. No fabricated chart data.
- Maximum market leverage selected by default, adjustable down to 1x; size-sensitive limit checked again by the worker.
- Default duration 30 seconds; 1, 3 and 5 minute options. The timer starts from the confirmed opening order's completion timestamp and displays minutes:seconds. With strictly less than 60 seconds remaining, Increase time offers the same 30s/1m/3m/5m increments, added to the current deadline. Repeat on later countdowns without a total lifetime cap. Extensions cannot revive expired, closing or externally ended positions; more time does not prevent liquidation or guarantee profit.
- USDC margin input defaults to $5, with $5/$10/$25/$50 quick presets and Max inside the input. Smaller custom amounts remain allowed. Presets, Max and starting a round share checks for USDC-only capacity, live orderbook reference prices, account-specific leverage/IMR limits and market quantity limits. Sizing reserves at least 10% extra margin for the observed opening allocation plus a 0.5% capacity cushion; this is execution headroom, not an extra trading fee. Max rounds down to cents. Exchange execution and balance changes can still affect acceptance.
- The main screen shows “Your result” with “Estimated · fees included” and a personalized break-even chart line covering both entry and exit fees. Detailed cost explanations are in the collapsed “Good to know” FAQ; actual fills and fees remain in portfolio history. Confirmed partial closes are included; unreconciled fills and disconnected streams show a waiting state. Mark-based estimates exclude funding and are not guaranteed closing proceeds. Results begin below zero after costs and only turn green when net positive. Up and Down execute directly using the displayed settings, without a per-round dialog or checkbox. Wallet authorization is requested only when this browser has no usable device authorization. The dedicated game key persists across reloads and return visits, with a wallet-signed 365-day expiry. A synchronous submission guard prevents rapid duplicate clicks; account changes during signing cancel the pending entry. Authorization details remain in the FAQ.
- Account value, USDC balance, deposit and withdrawal dialogs using the existing Orderly components.
- Portfolio overview (daily/cumulative PnL), balances, positions, orders and history. Local round history adds entry/exit fills, price direction, gross PnL, fees, net trading PnL and profitable-round counts. A correct direction with a net loss is labelled when fees exceeded the gain. Funding is excluded from round PnL and remains in the account portfolio.
- API-key management is absent from the mounted routes and navigation. Internal Orderly key authorization is still necessary for trading.
- Cato amber/cream colours, fonts and cat artwork; mobile layouts and accessible native dialogs.

## Timed round service

The user authorizes a separate 365-day Orderly key with read,trading permissions through their wallet. It is NOT a close-only credential. The browser's dedicated device-authorization manager stores it in localStorage, namespaced by wallet address, account, network and broker, separately from the SDK's key. It restores and verifies public key identity, active status, scopes and actual registered expiry before reuse. Temporary network/rate-limit failures preserve the saved key instead of triggering another signature. Concurrent calls are serialized within the page and across tabs with Web Locks where available. Storage-blocked browsers retain an in-memory session but cannot retain it after closing the page. This uses the SDK's browser-storage model: same-origin scripts can access the trading credential, and no encryption-at-rest guarantee is made. The wallet private key is never stored.

The browser sends the dedicated key only to the local service when submitting a round or requesting more time. Extensions authenticate the supplied account/key, verify read/trading-only scope and an expiry beyond the new deadline plus one minute, then persist the deadline and credential together. No key is exposed through round responses. The service cannot submit withdrawals through any of its routes. The signed expiry is fixed; revisiting does not silently extend it. The first use after this upgrade needs one new wallet authorization because the old one-day in-memory keys were never persisted. There is no recurring consent dialog or new main-screen reminder.

The game plays one market, `PERP_BTC_USDC` (`GAME_SYMBOL` in app/game/market.mjs, shared by the bundle, the local worker and the website's round service). The round service refuses any other symbol ("Only BTC is playable.") and always opens at the market's live, size-sensitive maximum leverage for the requested amount; a leverage value in the request is ignored. `/game-api/markets` returns that single row (with its current `maxLeverage`), or no rows while BTC is not active for the broker. There are no price routes: the mark-tick recorder and `/game-api/marks` / `/game-api/candles` were removed; the chart is built in the browser from the round's own PnL.

The worker validates market/size, checks for existing positions and orders, and writes opening intent to an encrypted journal before submitting any order. The opening order is a maker (post-only) quote at the top of the book: UP buys at the best bid, DOWN sells at the best ask (the signed `GET /v1/orderbook/{symbol}?max_level=1` snapshot, snapped to the market's `quote_tick` away from the spread, a bid down and an ask up, so the snap itself never crosses; an empty or crossed book places nothing until the next tick, and the maker window still runs from the opening intent: if it ends with no quote ever placed and the book still unusable, the round fails with "No usable order book" rather than sending a market order into it). While the round is `opening` the engine ticks about once a second: it reads the quote by client order ID (`{prefix}-q{n}`), records partial fills, and when the top of the book moves away from the quote (or the player cancels, or the maker window ends) it saves a cancel intent, sends the cancel and waits until Orderly reports the order terminal (CANCELLED/FILLED) with its final filled quantity; only then does it place a new post-only quote for the remainder under a new client ID. A post-only quote Orderly refuses (it would have taken) is a definitive non-fill and is requoted on the next tick. `MAKER_WINDOW_S` (20s, server/engine.mjs) after the first quote, an unfilled remainder is bought or sold with a market order (`{prefix}-m`) once the resting quote is confirmed cancelled; what the quotes filled is kept. The round opens when the planned quantity is filled (or when the market fallback finishes): the entry price is the volume-weighted average of every fill, `openFee` is their sum, and the deadline runs from the time of the last fill. The public round carries `fill = { filledQuantity, quantity, quotes, maker, fallback }` for the UI (never credentials or raw exchange rows); the attempts themselves live in the round's `openAttempts`. Rounds journalled before maker quotes existed (one market order under `openClientId`) are still finished with whatever that order filled. At the deadline it submits an opposite-side reduce-only isolated market order, verifies fills, retries confirmed incomplete closes, and verifies a flat position before reporting a completed result. An early-close button requests the same process.

`POST /game-api/rounds/:id/cancel` (same authorization as the other round routes) cancels a round that is still `opening`: the request is recorded with a compare-and-set write (no order) and the round advanced at once; the resting quote is cancelled and confirmed, and if anything had filled that part is closed reduce-only and the round ends as `ended_early` with its confirmed result (`closeReason: "cancelled"`, `resultPending: false`); if nothing filled the round fails with "Cancelled before fill", no position and no stored credential. Once a round is `open`, only "Close round early" applies. The browser shows the opening as "Placing your call… → Waiting for a fill at the best price… → Locked in!" with "Filled 40%" once a partial fill is reported, a small Cancel link while opening, and "Finishing the fill…" after the maker window. A quote Orderly cannot find yet (a lost acknowledgement) is cancelled by client ID as soon as the player cancels or the window ends, and kept under watch; the round's error reads "Confirming whether the quote reached Orderly…" meanwhile and the sending block shows it. A player's cancel sends no cancel for a pending market fallback (nothing rests): the round waits for its terminal state and then closes what it filled. Extension authentication runs outside the scheduler lock so a slow network check does not delay closing. The commit rechecks the live deadline and status under the same per-round lock as reconciliation. Each extension has a durable request ID: retries cannot add time twice, including across worker restarts. If a response is unclear, the UI retries only the same increment until the journal confirms it.

Only one active round per account is permitted. This draft requires an account with no existing positions or pending orders and supports main accounts only. Do not trade the same account through another interface during a round. The Orderly account and balance belong to the wallet and broker, so they are shared with any other Orderly interface used with the same wallet; this is not a separately funded game wallet.

Legacy missing outcomes can be recovered through the local `/rounds/:id/reconcile` route with a saved dedicated device key. This route verifies the authenticated account, reads position history, and persists only the matched result (or a small candidate history record for diagnosis), never the supplied credential. Background recovery cannot create a key or trigger a signing prompt. The SDK history fallback uses its default unwrapped rows array.

Deadlines, including accepted extensions, survive tab closure and service restarts. A restart resumes reconciliation; it does not recreate an opening order. If the computer sleeps or the worker stops, closing cannot occur until it resumes. A timeout means the close is due, not that a closing fill is guaranteed. Liquidation or external closure is matched to a fully closed isolated position by market, side, opening time, price and quantity. Until a unique complete record arrives the UI shows "Confirming result". The SDK's position-history net-PnL formula includes funding; liquidation fee details must not be subtracted twice. Older records without a worker credential recover through the browser SDK's authenticated history query. The chart uses the SDK's current estimated isolated liquidation price and marks confirmed liquidation events within the visible time window.

Ambiguous order-submission responses are reconciled by client order ID, never blindly resubmitted. If an intent was persisted but the process stopped before sending it, or an order remains unresolvable, the round stays pending and reports the error. Inspect Portfolio and close manually if required; this draft does not silently assume no order exists. Exchange outages, revoked/expired credentials, closed market sessions, and position changes can prevent scheduled closing.

By default the .runtime directory holds an AES-GCM encrypted journal and its local machine key. Both are gitignored and blocked from Vite file serving. Encryption protects against accidental journal disclosure; a process/user that can read BOTH files can decrypt it. This is local development storage, not production key custody. Setting DATABASE_URL (a server-only variable, never VITE_*) moves the journal to the website database instead: one row per round in the updown_rounds table (db/0011_updown_rounds.sql, applied with `npm run migrate` in this app; it shares the schema_migrations ledger with cato-wrapped's packages/db migrator). Hot columns (account, market, direction, status, bet, leverage, duration, result, timestamps) are real columns; the full round object is the `data` JSONB column; the round credential is sealed with AES-256-GCM under UPDOWN_JOURNAL_KEY (64 hex characters from secret storage; required with DATABASE_URL, the worker refuses to start without it rather than sealing shared rows with the .runtime machine key) and cleared once the round no longer needs it. Only the game layer is stored; fills, fees, balances and transfers stay in Orderly. Every state change is committed before the next order is sent, so the "intent before send" rule holds in both modes. Reconciled or failed rounds remove their credential from the current journal. An externally closed position retains its credential while read-only position-history requests confirm its final result, without submitting further orders for that round. The separate Orderly authorization expires at its wallet-signed deadline (365 days for new device authorizations); removing a local credential does not revoke that authorization remotely.

The local worker binds only to loopback, rejects cross-origin requests and unexpected hosts, requires a random local session token, and exposes specific game endpoints rather than a generic trading proxy.

## Serverless round service (the website on Vercel)

apps/web/app/game-api/[...path]/route.ts serves the same endpoints as server/index.mjs through server/service.mjs, as Node serverless functions:

- Authentication is the site's signed session cookie (no token; /game-api/session returns the network and signed-in wallet). Requests a browser labels cross-site, foreign Origin headers and non-JSON POSTs are refused.
- Authorization: every round list, start, extension, early close and reconciliation is limited to the Orderly account of the session's wallet on this broker (public `GET /v1/get_account?address=&broker_id=&chain_type=SOL`, cached per instance; Orderly code -1607 means the wallet has no account yet). Other accounts and their rounds get 403.
- State lives only in Postgres. DATABASE_URL and UPDOWN_JOURNAL_KEY are required (there is no file journal); db/*.sql is applied automatically on first use under a transaction-scoped migration lock, over DATABASE_URL_UNPOOLED when present (UPDOWN_AUTO_MIGRATE=0 to disable and run `npm run migrate` here instead, which also prefers DATABASE_URL_UNPOOLED). Everything is safe through Neon's transaction-mode pooler: no session state and no named prepared statements. TLS is certificate-verified for remote hosts (server/pg-ssl.mjs).
- Concurrency: any number of invocations may tick the same round. Each one takes a database lease (table updown_locks) on the round and skips it if another holds it, and every journal write is a compare-and-set on the row's version, so two invocations can never both persist a close intent and send it. Intent is still committed before every order. Starting a round takes leases on the account and the round, and the unique index updown_rounds_one_active_idx still allows one active round per account. Leases rather than advisory locks: session advisory locks do not survive Neon's transaction-mode pooling, and orders must be sent outside any transaction so their intent is committed first. A round lease lasts 90s (`leaseMs` in server/postgres-store.mjs): longer than the slowest tick, so a live holder is not overtaken. Flat-position counters, the reconcile throttle and the last tick time live in the round's data.
- Ticking without a process: a player's /game-api/rounds poll (every 1.5s while the game is open) advances that account's rounds, at most about once per second per round. Vercel Cron calls /api/updown/sweep every minute with `Authorization: Bearer ${CRON_SECRET}` (outside the sign-in gate); one sweep at a time (lease "sweep") advances every due round, sleeps ~1s and repeats for up to ~55s, and exits at once when nothing is due. An abandoned round therefore closes within a few seconds of its deadline. Downtime of Vercel, the database or Orderly still delays closing; a countdown never guarantees a closing fill.
- Time budget: /game-api runs with maxDuration 120s and the sweep with 120s. The sweep starts no new round after 75s, leaving 45s for the slowest one in flight (a position read, an order lookup and a close, each with a 10s timeout), so an order is never the last thing running when the platform cuts a function off. An early close never waits for a busy round: it records closeNow (a compare-and-set write, no order) and whoever holds the round, or the next sweep, closes it.
- Orders that never reach Orderly: each attempt records its send outcome (ackAt, sendFailedAt, rejectedAt). If Orderly still has no record of an order (lookup code -1006) 105s after its intent was saved (the 90s lease plus the 10s request timeout; 5 minutes if Orderly had acknowledged it), it was never received. A missing close is finished with nothing filled and the next tick sends c{n+1}, reduce-only like every close, so a late duplicate can only reduce the position. A missing opening attempt is decided by the account's position on that market: a position equal to what the other attempts filled means it was never received, so a quote is abandoned and replaced, a market fallback keeps the fill so far, and a round with nothing filled fails; an attempt a partial fill was already read from is never abandoned (it demonstrably reached Orderly): it is cancelled, idempotently, and polled until it shows again. An abandoned quote is cancelled anyway, and nothing else is placed until Orderly confirms that cancel (acknowledged, or refused as unknown; an ambiguous cancel is sent again). Before every further opening order and before the round opens, abandoned quotes are looked up once more: one that arrived late is cancelled while it rests, and a fill of one counts in the round's quantity and entry instead of pausing the round as a position changed outside it; a larger position in the round's direction, within its size, means it did execute and the round adopts it (entry from the position's average open price, result confirmed from Orderly's position history after the close); any other position is left untouched. A position flattened by hand is detected even while a close attempt is unresolved. Abandoned attempts are looked up once more before a result is reported, so a late fill still counts.
- Opening quotes under concurrency: exactly one opening attempt is live at a time. Every quote, market fallback and cancel has its intent written (compare-and-set, under the round's lease) before the request, so an invocation that dies between the intent and the send, or two invocations ticking the same round, can only find the intent and look the order up by its client ID, never place it twice. A cancel on record without an acknowledgement (or whose order still rests 2s after one) is simply sent again: cancelling is idempotent and can never add a fill.
- Definitive close rejections (e.g. a revoked key, Orderly code -1002) are retried with exponential backoff (2s doubling, capped at 5 minutes) and the round's error says so; at most 20 close attempts are kept per round (older ones that filled nothing are dropped). Other definitive errors back off up to 60s per round. An explicit close request skips the backoff.
- Networks: VITE_DEPLOYMENT_ENV is read by one parser everywhere (app/utils/deployment-network.mjs): trimmed, case-insensitive, unset = testnet, anything but mainnet/testnet is an error (the build fails, the service answers 503). A mainnet build also requires VITE_DISABLE_MAINNET=false and VITE_DISABLE_TESTNET=true so the page cannot drift to testnet. After a network change, the sweep keeps closing rounds still live on the previous network with that network's Orderly base (server/sweeper.mjs); new rounds start only on the configured one.
- Preview deployments: mainnet play and the sweep are refused (503) on any Vercel deployment whose VERCEL_ENV is not production, unless UPDOWN_ALLOW_PREVIEW_MAINNET=1. Scope DATABASE_URL, UPDOWN_JOURNAL_KEY and CRON_SECRET to Production only; a preview that should play uses testnet with its own database and journal key.
- Account IDs are stored and compared lowercase (db/0013 adds a lower(account_id) index and, when the data allows, a case-insensitive one-active-round index). A terminal row never keeps a credential: the store writes NULL for any round without pending work.

## Open questions

- Reduce-only closes below the minimum order size: when a maker quote fills only dust (less than the market's `base_min`, or under `min_notional`) and the player cancels, or a close leaves such a remainder, the reduce-only close for that quantity may be refused by Orderly's size checks. Whether Orderly accepts a reduce-only order below `base_min` for the purpose of flattening a position is not confirmed; until it is, such a remainder shows as a rejected close with its backoff message, and the player closes it in Portfolio.
